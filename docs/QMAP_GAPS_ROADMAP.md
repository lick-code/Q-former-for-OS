# QMAP 训练缺口清单 + 补齐路线图

本文档整理当前 `QMAP` 原型在“可正式训练、可复现实验、可扩展评估”方面的主要缺口，并给出对应的补齐路线图。

> 说明：这里讨论的是 `cache_replacement/qmap/` 这条新增链路，而不是原始 PARROT cache replacement 训练流程。

---

## 总览

当前仓库已经具备：

- QMAP 数据生成器：`qmap/qmap_generator.py`
- QMAP 训练脚本：`qmap/qmap_train.py`
- QMAP 评估脚本：`qmap/qmap_eval.py`
- 集成测试：`qmap/qmap_integration_test.py`
- 少量示例 trace / jsonl 样例

但如果目标是进入“正式训练 + 正式实验”的状态，还缺少一整套数据、实验与评估基础设施。

---

## 1. 训练数据集缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 正式训练数据集 | 目前只有少量示例 trace 和 toy jsonl，更多是 smoke test 用途 | 模型难以学到稳定模式，实验结果不可靠 | 收集更大规模 trace，批量生成 `train_data.jsonl` / `valid_data.jsonl` / `test_data.jsonl` | P0 |
| 多 trace 混合训练集 | 现在更像单 trace 原型 | 泛化能力不足，容易过拟合某一 workload | 汇总多个 workload trace，统一格式后混合训练 | P0 |
| 标准 train/valid/test 切分 | 当前训练脚本只直接吃一个训练文件 | 无法做模型选择和泛化评估 | 增加固定切分脚本或切分规则，确保不泄漏 | P0 |
| 数据集版本管理 | 目前样本来源和生成配置不够标准化 | 结果不可追溯，难以复现 | 给数据集加版本号、生成配置和元数据记录 | P1 |

### 补齐建议

先优先把数据集做成下面这种结构：

```text
qmap_dataset/
  raw/
    trace_a.csv
    trace_b.csv
  processed/
    train.jsonl
    valid.jsonl
    test.jsonl
  metadata/
    generation_config.json
    split_config.json
```

## 2. Trace 获取与清洗缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 自动批量 trace 转换 | 现在主要依赖手工执行脚本 | 流程容易出错，不适合多实验重复跑 | 增加批处理脚本，把多个 CSV 自动转成 JSONL | P0 |
| trace schema 校验 | 目前只做了有限字段检查 | 非法数据可能静默进入训练链路 | 加强输入校验，统一 CSV 列名与 RW 编码 | P0 |
| trace 清洗规则 | 还没有统一过滤坏样本、截断、分段的规范 | 数据质量不稳定，训练波动大 | 增加清洗步骤，并记录被过滤样本原因 | P1 |
| RW 编码统一 | 目前支持多种 RW 表达，但还缺统一规范 | 不同 trace 间可能存在编码不一致 | 统一转换成 `0/1` 或 `R/W`，在入口处标准化 | P1 |

### 补齐建议

把 trace 处理拆成三步：

1. 原始 trace 导入
2. 校验与清洗
3. 样本生成

这样后续排查问题会清晰很多。

## 3. 标签定义与质量缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 标签定义文档 | 当前标签更多是代码实现逻辑，缺少系统化说明 | 很难判断监督信号是否合理 | 写清每个字段的物理意义、计算方式和假设 | P0 |
| 标签与真实目标一致性 | 当前训练目标偏原型化，不一定完全等价于真实迁移代价 | 模型可能学到“看起来对，但实际不对”的策略 | 明确训练标签和评估目标的对应关系 | P0 |
| 标签噪声控制 | 启发式 / 模拟标签可能带来噪声 | 训练不稳定，效果上限受限 | 对标签进行统计分析，必要时做平滑或重采样 | P1 |
| 标签生成可追溯 | 生成过程没有足够元数据记录 | 难以定位某个样本为什么是这个标签 | 在 jsonl 旁边记录生成参数和来源 trace 信息 | P1 |

### 补齐建议

至少要把下面几件事写清楚：

- `inactivity` 是怎么定义的
- `coldness` 是怎么计算的
- `write_sensitivity` 的含义是什么
- `migration_cost` 如何估计
- 这些字段是否对应真实系统成本

## 4. 数据分布与泛化缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| workload 覆盖不足 | 目前可能只覆盖少数 trace | 模型泛化差 | 增加读多、写多、混合、热点、长尾等多种 workload | P0 |
| 长序列样本不足 | 训练是否覆盖足够长的局部性模式还不明确 | 模型可能只能学短期相关性 | 构造更长 trace 或更大 history window | P1 |
| 并发 / 多程序场景缺失 | 目前更像单流 trace | 与真实系统差距大 | 引入多程序并发访问 trace | P2 |
| 分布统计不明确 | 还没有对 trace 统计特征做系统分析 | 很难判断数据是否有偏 | 统计访问频率、写比例、reuse distance 等 | P1 |

### 补齐建议

先做一份数据统计报告，至少包含：

- 总访问数
- 唯一页数
- 读写比例
- reuse distance 分布
- 热点页集中度

## 5. 训练工程化缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 统一配置文件 | 当前训练参数主要靠命令行 | 参数管理不方便，实验复现成本高 | 增加 JSON / YAML config 文件 | P1 |
| validation 逻辑 | 训练脚本目前没有正式验证流程 | 无法选最优 checkpoint | 在训练中加入 valid 评估与 best checkpoint 保存 | P0 |
| early stopping | 没有早停机制 | 训练时间浪费，过拟合难控制 | 基于 valid loss / hit rate 增加早停 | P2 |
| resume training | 断点恢复能力不完整 | 长训练容易中断后重来 | 保存 optimizer、epoch、config 并支持恢复 | P1 |
| 学习率调度 | 当前学习率固定 | 收敛速度和最终效果可能受限 | 增加 scheduler | P2 |
| 随机种子固定 | 可复现性不够强 | 同配置结果波动较大 | 固定 Python / NumPy / Torch seed | P0 |
| 日志规范 | 训练输出主要是 print | 不利于分析和对比 | 增加 tensorboard / wandb / structured log | P1 |

### 补齐建议

训练脚本至少应该支持：

- `train`
- `valid`
- `save best`
- `resume`
- `seed`

这是进入正式实验的最低配。

## 6. 评估闭环缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 多 trace 批量评估 | 现在更像单次 replay | 难以形成 benchmark 结论 | 写批量评估脚本，统一汇总多个 trace 结果 | P0 |
| baseline 统一对比 | 虽然支持 `lru/random/qmap`，但还不够体系化 | 结果难横向比较 | 统一输出表格和汇总指标 | P0 |
| checkpoint 自动选择 | 目前要手动挑模型 | 实验流程繁琐且易错 | 根据 valid 指标自动选择最佳 checkpoint | P0 |
| 结果汇总 | 缺少统一 report | 不便写实验结论 | 生成 CSV / Markdown 汇总表 | P1 |
| 成本模型更精细化 | 现在是固定 cost 常数 | 评估可能过于简化 | 根据更真实的 DRAM/NVM 模型调整成本 | P2 |

### 补齐建议

把评估流程做成：

1. 对所有 trace 批量 replay
2. 自动读取最佳 checkpoint
3. 输出统一结果表
4. 生成对比图或 markdown 报告

---

## 7. 系统对接缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 与真实页迁移系统对接 | 当前还是原型 replay | 不能直接用于系统验证 | 接入更真实的 page migration pipeline | P2 |
| 在线决策链路 | 目前是离线训练 / replay | 不能验证在线推理开销 | 增加在线推理和决策接口 | P2 |
| 硬件/OS 级成本建模 | 还不是系统级真实成本 | 指标和真实部署可能偏差大 | 引入更接近内核/硬件的模型 | P2 |

### 补齐建议

如果短期目标是论文实验，先不用急着补这一层；如果目标是系统落地，这一层是必须补的。

---

## 8. 文档与使用门槛缺口

| 缺口项 | 为什么缺 | 影响什么 | 怎么补 | 优先级 |
|---|---|---|---|---|
| 训练流程文档统一 | 当前分散在 README 和多个说明文件里 | 新人上手成本高 | 汇总成单一训练手册 | P0 |
| 命令行示例规范 | 目前命令分散、路径写法不统一 | 容易路径错误 | 提供标准 bash 脚本模板 | P0 |
| 输出目录约定 | checkpoint / log / data 没有统一规范 | 容易混乱 | 固定目录结构和命名规则 | P1 |
| 常见错误排查 | 缺少 FAQ | 报错后不容易定位 | 增加常见报错与解决方法 | P1 |

### 补齐建议

建议统一成：

```text
cache_replacement/
  qmap/
  scripts/
  docs/
  data/
  qmap_checkpoints/
  logs/
```

## 补齐路线图

### Phase 1：先把“能正式训练”补齐
优先级最高，建议先做这些：

- 建立正式训练数据集
- 固定 train/valid/test 切分
- 加强 trace schema 校验
- 补 validation 和 best checkpoint 保存
- 固定随机种子
- 写统一训练脚本

### Phase 2：把“能做可信实验”补齐
第二阶段建议做：

- 多 workload 覆盖
- 标签定义文档
- 数据统计分析
- 批量评估脚本
- baseline 统一对比
- 结果汇总报告

### Phase 3：把“能扩展到系统级”补齐
如果后续要继续往真实系统推进，再做：

- 更真实的成本模型
- 在线决策接口
- 系统级 page migration 对接
- 更大规模并发 trace

---

## 推荐优先级

### P0：立刻要补

- 正式训练数据集
- train/valid/test 切分
- validation 流程
- 固定随机种子
- trace 校验
- 标准化训练脚本

### P1：尽快补

- 数据集版本管理
- 标签定义文档
- 多 trace 混合
- 日志规范
- 批量评估和结果汇总

### P2：中长期补

- 早停、scheduler、resume
- 更真实的系统成本模型
- 在线推理与系统对接
- 更完整的 benchmark 框架

---
