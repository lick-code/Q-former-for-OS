# CAPD Stage10A Async Simulator Design

**Status:** design approved; Stage10A implementation authorized.

**Goal:** Build a deterministic, reproducible, single-threaded discrete-event simulator for CAPD asynchronous page admission, background demotion, queue pressure, free-frame exhaustion, emergency fallback, and foreground blocking, without claiming Stage10B or real Linux behavior.

## Scope and authority boundary

This design implements Stage10A only. It does not run the Stage9 90-job Replay, consume the historical `stage9-overhead-r1` failure as a measurement, or generate a formal asynchronous result. It does not modify Stage8 r5 evidence, Stage9 r1 evidence, CAPD `F_low`/`F_target`/`b_max` semantics, promotion, Placify, multiprocessing, multithreading, or kernel integration.

The implementation accepts the existing Stage8 r5 authority only for a future Stage9 receipt gate. Fixture mode uses explicit synthetic parameters and does not read Test data for parameter selection. Formal mode is fail-closed until a new Stage9 v2 receipt proves `stage9_overhead_verified` and all required CPU, hardware-counter, RSS, manifest, verification, SHA, and Stage8 r5 bindings.

The inspected authority snapshot is:

- Stage8 r5: `CAPD-PROACTIVE-STAGE8-2.0`, `stage8_sync_replay_verified`, 80 jobs (48 Standard, 32 Pressure), 10 track-workload cells, and 30 CAPD jobs.
- Stage9 configuration: `CAPD-PROACTIVE-STAGE9-2.0`, implemented and awaiting new Linux measurement.
- Historical Stage9 r1: `stage9_not_verified`, blocked by `kernel.perf_event_paranoid=4` and unsupported perf events; its directory remains immutable.
- Read-only tree digests recorded before implementation: Stage8 r5 `554eba14afa57eab2e02aaa156f32181d29d4c66929a5fd2ca934e87c5cf49db`; Stage9 r1 `805c73bf0f280799817f481ef4a3cbab2d470de2c40adcf78d081f1f15a96a7b`.

## Architecture

Use implementation path A: a standalone pure-Python Stage10 module and runner.

- `qmap/proactive_stage10.py` owns typed configuration validation, event records, arrival generation, the simulator state machine, metric aggregation, and formal-receipt checks that do not require Linux-only imports.
- `scripts/run_capd_proactive_stage10.py` owns CLI parsing, run-directory lifecycle, fixture scenario execution, artifact assembly, manifest/SHA generation, and independent verification.
- `configs/finals/capd_proactive_stage10.json` declares all fixture and runner inputs; no timing or capacity parameter is hidden in production constants.
- `configs/finals/capd_proactive_stage10_result_schema.json` describes artifact and metric fields.
- `tests/test_capd_proactive_stage10.py` contains small synthetic fixtures only.
- `docs/CAPD_PROACTIVE_STAGE10_PROTOCOL_CN.md`, `docs/CAPD_PROACTIVE_STAGE10_STATUS_CN.md`, and `docs/CAPD_PROACTIVE_STAGE10_SERVER_CN.md` document semantics, status, and copyable server handoff commands.

The simulator imports no PyTorch, `resource`, or perf module. Formal measurement remains explicitly separate and must reject non-Linux or incomplete Stage9 evidence rather than estimate it.

## Time and event ordering

All internal timestamps are non-negative integer nanoseconds (`time_unit=ns`). `T_inference`, `T_migration`, the simulation horizon, and generated arrival times share this unit and must be positive where applicable. Floating-point wall-clock estimates are not accepted.

Events are stored in a heap with the explicit key `(timestamp_ns, event_priority, event_id)`. `event_id` starts at one and increases exactly once for every scheduled event. The fixed priority table is:

| Priority | Event |
| ---: | --- |
| 0 | `demotion_finish` |
| 1 | `capd_inference_finish` |
| 2 | `capd_round_start` |
| 3 | `emergency_fallback` |
| 4 | `page_enter_dram` |

This ordering releases completed frames before simultaneous arrivals. An emergency event generated by a page arrival is processed before remaining same-time page arrivals. No behavior depends on Python dictionary insertion order or incidental heap ordering.

## State machine and event semantics

The model has one DRAM frame pool, one FIFO foreground blocked-request queue, and one serial background service. Background service states are `idle`, `inference`, and `migration`; inference and migration never overlap.

The simulator maintains one authoritative reservation set:

```text
reserved_page_ids =
    inference_selected_page_ids
  union active_migration_page_ids
  union pending_normal_migration_page_ids
  union pending_emergency_migration_page_ids
```

Every new inference selection and every emergency selection excludes `reserved_page_ids`. The four components must be pairwise disjoint, every reserved page must still be resident until its `demotion_finish`, and insertion of an already-reserved `page_id` is an immediate contract error. This assertion is checked after every event, so the same page cannot be inferred, queued, migrated, or removed twice.

Initialization is fully deterministic. `initial_resident_count = dram_capacity_frames - initial_free_frames`; initial resident page IDs are the integers `0` through `initial_resident_count - 1`. The stored LRU order is MRU-to-LRU `[0, 1, ..., initial_resident_count - 1]`, so the initial LRU tail in oldest-first order is `[initial_resident_count - 1, ..., 1, 0]`. New arrival page IDs continue monotonically from `initial_resident_count` and are inserted at the MRU head in event-processing order.

`page_enter_dram` counts an arrival attempt. If a free frame exists, one frame is consumed, a deterministic page ID is appended to resident state, and a low-watermark round may be scheduled. If no frame exists, the request is appended to the blocked FIFO and an `emergency_fallback` is scheduled at the same timestamp; admission is deferred until a later demotion releases a frame.

`capd_round_start` is eligible only when no background task is active and `0 < F_t < F_low`. The frozen `candidate_source=lru_tail` rule scans resident pages from oldest to newest, excludes all `reserved_page_ids`, and takes at most explicit `K`. The ordering key is `(lru_tail_rank, page_id)`, so `page_id` is the final tie-break if equal recency is ever represented. The batch size is exactly `b_t = min(b_max, F_target - F_t, candidate_count)`. The first `b_t` page IDs in this deterministic abstract-service order enter `inference_selected_page_ids` before inference begins. This assignment models page occupancy and service timing only; it is not reported as CAPD ranking quality or used to alter Stage8 evidence. A zero batch does not schedule inference or migration.

`capd_inference_finish` moves the already-reserved selected page IDs atomically from `inference_selected_page_ids` to the ordinary pending migration component without changing their membership in `reserved_page_ids`. Each job completes after exactly `T_migration`; the service processes one job at a time.

`emergency_fallback` records fallback count, triggering page ID, free frames, background queue length, and the blocking start timestamp. If pending or active work cannot provide one release per blocked request, it selects only from resident pages outside `reserved_page_ids` and inserts deterministic oldest-resident emergency migration jobs at the front of the not-yet-started service queue. Emergency work cannot preempt an already-running inference or migration.

If the background service is idle when emergency work is inserted, the first emergency migration starts immediately. If inference or migration is already active, the emergency job waits at the head of the pending queue and starts at the next service boundary.

`demotion_finish` removes its page from the active migration component and `reserved_page_ids`, removes that resident page exactly once, and releases one frame. The oldest blocked request, if any, immediately consumes that frame and becomes resident; its blocking duration is `finish_time - blocked_start_time`. Otherwise the free-frame count increases. The event updates demotion counters, starts the next queued migration, and may schedule the next CAPD round.

The invariant `free_frames + resident_page_count == dram_capacity_frames` is checked after every event. Negative free frames and capacity overflow are contract errors; a fallback is a recorded model event, not permission to violate the invariant.

## Inputs and arrival generators

Required explicit inputs are `T_inference_ns`, `T_migration_ns`, `b_max`, `b_t_reference`, `dram_capacity_frames`, `initial_free_frames`, `F_low`, `F_target`, `K`, `simulation_horizon_ns`, `seed`, and an arrival model. `initial_free_frames` must be within `[0, dram_capacity_frames]`; `initial_resident_count` is derived exactly as `dram_capacity_frames - initial_free_frames`; `b_t_reference` must be an integer in `[1, b_max]`; all durations and capacities must be positive or explicitly bounded by their stated domain.

Each experimental scenario declares `b_t_reference` for offered-load construction. Its model-derived service capacity is `mu_demote = b_t_reference / (T_inference + b_t_reference * T_migration)`, matching the Stage10 plan. Periodic scenarios use the four required ratios `0.5`, `0.8`, `1.0`, and `1.2` of this value and generate integer-nanosecond fixed intervals using deterministic fixed-point arithmetic. Runtime rounds still compute the actual `b_t = min(b_max, F_target - F_t, candidate_count)`; every actual value and its distribution are recorded. `b_t_reference` is a load-generation input, not a claim that every round attains that batch size.

Burst scenarios declare a base rate and one or more non-overlapping intervals. Each interval supplies either an absolute rate or a multiplier, a start time, and a duration. A seed-derived integer phase selects the first arrival in each interval; subsequent arrivals use the exact integer period for that interval. This keeps the declared rate exact, supports multiple bursts, and makes the event sequence reproducible without floating-point random sampling.

## Metrics and interpretation

The output separates `observed`, `derived`, and `interpretation` objects.

Observed fields include `emergency_fallback_count`, `fallback_rate`, `foreground_blocking_time_total`, `foreground_blocking_time_mean`, `foreground_blocking_time_p95`, `blocking_sample_count`, `minimum_free_frames`, `free_frame_exhaustion_duration`, `background_queue_length_mean`, `background_queue_length_max`, `background_queue_length_p95`, `background_utilization`, `page_enter_dram_count`, `demotion_finish_count`, `effective_demotion_rate`, and `unfinished_blocked_request_count`.

Queue mean/P95 and exhaustion duration use event-interval time weighting over the fixed simulation window. Blocking statistics use completed blocked requests only and report `blocking_sample_count`. With no completed blocked requests, `foreground_blocking_time_mean` and `foreground_blocking_time_p95` are JSON `null`, `blocking_sample_count` is zero, and human-readable reports show `N/A`; this is distinct from an observed zero-duration block. `foreground_blocking_time_total` remains zero because it is an additive total over an empty sample. `fallback_rate` is fallback events divided by page-enter attempts, and `effective_demotion_rate` is completed demotions per simulated second.

Derived fields include `simulation_horizon_ns`, `seed`, `T_inference_ns`, `T_migration_ns`, `b_max`, `b_t_reference`, reference `mu_demote`, the actual per-round `b_t` distribution, arrival model, load ratio, and burst parameters. Interpretations describe only what was observed within the simulated horizon; they never use language implying real Linux CPU utilization, kernel behavior, foreground end-to-end latency, or measured asynchronous concurrency.

## Fixture and formal gates

Fixture mode requires an explicit `mode=fixture` marker and synthetic timing/state values. It may run unit tests and small candidate scenarios, including no-arrival, all four periodic load ratios, and at least one multi-burst scenario.

Formal mode requires a Stage9-owned receipt whose status is `stage9_overhead_verified`, whose verification proves real Linux CPU latency, cycles/instructions/task-clock, and RSS, and whose manifest, verification, SHA chain, and Stage8 r5 authority hashes agree. Any path or identity referring to `stage9-overhead-r1` is rejected. A failed formal gate prints a structured reason, returns non-zero, and does not write a formal result artifact.

## Candidate artifacts and statuses

The fixture candidate run is written under `outputs/capd_proactive_stage10/stage10-async-simulator-r1/` and contains `config.json`, `event_model.md`, `parameters.md`, `fixture_results.jsonl`, `test_log.txt`, `formal_gate.json`, `verification.json`, `run_state.json`, `manifest.json`, `SHA256SUMS`, and `README.md`.

After local verification, `run_state.status` is `stage10_simulator_tests_passed`; `formal_gate.status` is `stage10_formal_blocked_by_stage9`. The candidate also carries explicit booleans: `stage10_simulator_implemented=true`, `stage10_simulator_tests_passed=true`, `stage10_formal_blocked_by_stage9=true`, and `stage10_formally_verified=false`. No fixture output is labeled as a formal experiment.

Artifact hashing is non-recursive and deterministic. `manifest.json` lists SHA256 values for every payload artifact except `manifest.json` and `SHA256SUMS`. After the manifest is final, `SHA256SUMS` lists every file except itself, including `manifest.json`. Independent verification recomputes the manifest payload hashes first and then the complete `SHA256SUMS` entries.

## Tests and acceptance

Tests are written before implementation and use only small synthetic fixtures. They cover identical event sequences and metrics for identical inputs/seed, fixed same-time priority, frame consumption/admission/release, fallback recording and blocking, empty blocking samples producing `null`/`N/A`, `b_t` bounds, duplicate reservation rejection, capacity and non-negative-frame invariants, deterministic initial LRU state and LRU-tail selection, no-arrival behavior, bounded low-load behavior within the finite window, explainable high-load queue growth, burst reproducibility, artifact hash verification, formal rejection while Stage9 is unverified, and prevention of fixture parameters being labeled formal.

Acceptance requires the pure-Python tests to pass, the fixture runner to produce a self-consistent candidate directory, independent recomputation of manifest/SHA and selected metrics to pass, and the formal gate to remain blocked. This is `candidate-ready`, never `stage10_formally_verified`.

## Server handoff boundary

The runner will provide copyable Linux commands for a future formal attempt using the repository's real script path, output directory, run ID, log path, and verification command. Those commands are documentation only until Stage9 supplies a verified receipt; this implementation does not claim that any server command has run.
