# CAPD 模块 3--5 分钟作品演示录制稿

## 演示目标

CAPD 是整个项目的两个模块之一，本段建议控制在 4 分钟左右。演示重点不是重复论文结论，而是让评委快速看清三件事：

1. CAPD 实验不是单个脚本，而是覆盖配置、数据、模型、回放、测试和证据归档的完整工程体系；
2. 仓库中的关键文件各自承担什么职责，实验产物如何被组织和验证；
3. 这些模块能够通过真实代码组成一次从输入到指标再到复现检查的演示闭环。

演示脚本使用独立合成负载，输出统一标记为 `non_formal_demo_only`。演示数值不等同于正式实验结果，不用于证明真实 NVM 性能、前台访问时延或异步并发性能。

## 录制前准备

在项目根目录先完成一次不录屏的预演：

```bash
test -f outputs/capd_proactive_stage4_stage7/stage4-stage7-unified-r2/checkpoints/opt-balanced/seed_3136859/qmap_best.pth
python -c "import torch; print('torch', torch.__version__, 'cuda', torch.cuda.is_available())"
python -m unittest -v tests.test_capd_demo
python scripts/show_capd_repository.py --skip-assets --pause 0
python -u scripts/run_capd_demo.py --device cpu --pause 0
```

正式录制时将终端调整为 16:9，放大字体至能看清约 90 个英文字符，关闭无关窗口和通知。建议保留一个终端窗口完成全部操作，不要临时使用 `tree -a` 或递归 `ls`，否则大量文件会快速刷屏。

## 时间轴、画面与口播

### 0:00--0:20 开场：CAPD 在项目中的位置

画面：终端位于项目根目录，先执行 `clear`，暂不滚动文件。

口播：

> 我们的作品由两个模块组成，接下来用大约四分钟介绍其中的 CAPD，也就是面向 DRAM/NVM 分层内存的上下文感知主动降级模块。这部分不重点展示结果有多好，而是带大家看一下我们围绕 CAPD 完成的实验体系、关键工程文件，以及整个实验链路如何闭环运行。

### 0:20--0:45 总览：实验分为哪些模块

画面：执行仓库导览命令。服务器磁盘较慢时可加 `--skip-assets`。

```bash
python scripts/show_capd_repository.py --pause 8
```

口播：

> CAPD 实验可以按功能分为五部分：第一是实验口径与配置契约；第二是访问轨迹和工作负载处理；第三是模型训练、冻结与推理；第四是多策略统一回放和指标计算；第五是自动化测试、验证和证据归档。这里显示的是当前仓库中与 CAPD/QMAP 直接相关的配置、源码、执行脚本、测试和文档数量，以及服务器上已经形成的 CAPD 实验资产规模。

说明：资产规模只表示当前服务器中的数据与产物体量，用于呈现实验工作量，不代表算法性能。

### 0:45--1:45 导览：关键目录和代表文件

画面：导览脚本会依次显示五类代表文件。不要再展开全部目录，跟随屏幕逐类讲解即可。

口播：

> `configs/finals` 保存实验配置和 JSON Schema。它们固定数据角色、候选集、主动降级参数、成本权重和结果字段，避免不同批次实验口径漂移。
>
> `dataset` 和工作负载脚本负责原始 trace、处理后数据以及训练、验证、测试角色的隔离。真实工作负载的来源、区间和摘要也会绑定到后续运行。
>
> `qmap/qmap_train.py`、`qmap/qmap_eval.py` 和模型冻结目录构成训练与推理链路。训练后不是直接凭文件名使用模型，而是通过 manifest 记录 seed、checkpoint 和 SHA-256 身份。
>
> `qmap/proactive_replay.py` 是多个策略共用的内存分层状态机；策略只替换候选页排序，访问处理、页迁移和计数规则保持一致。`qmap/proactive_cost.py` 再从原始事件独立计算加权成本。
>
> `tests`、`verification.json` 和中文实验文档组成验证与归档部分。测试检查状态守恒、策略边界和结果结构；运行目录保留配置快照、运行状态和校验回执，便于回查一次结果是如何产生的。

过渡句：

> 前面看到的是完整实验仓库。下面不重跑正式的大规模实验，而是用一个小规模、独立的合成负载，把相同的软件链路串起来，展示一次可以在几秒内完成的功能闭环。

### 1:45--3:35 运行：演示闭环

画面：执行以下命令，`--pause 0.5` 便于口播跟随。如果服务器 CPU 较慢，先实测后将 pause 调为 0。

```bash
RUN_ID="video-$(date -u +%Y%m%dT%H%M%SZ)"
python -u scripts/run_capd_demo.py --device cpu --pause 0.5 --run-id "$RUN_ID"
```

第一步口播：

> 首先是运行前检查。脚本加载实验契约和成本配置，并核对冻结 CAPD checkpoint 的 SHA-256。这样演示调用的是仓库中真实冻结模型，而不是临时构造的替代策略。

第二步口播：

> 接着生成一条确定性的合成内存访问序列。它与正式 Test 数据完全隔离，只用于功能演示；输入摘要会写入本次演示目录。

第三步口播：

> 然后在同一条访问序列上运行 Reactive-LRU、Proactive-LRU、Proactive-CLOCK 和 CAPD。四个策略共用同一 Replay 状态机，差异主要位于主动降级候选页的排序方式。CAPD 路径会实际加载冻结 checkpoint，并且只使用当前候选页和历史状态进行评分。

第四步口播：

> 运行后，脚本从 DRAM 命中、NVM 读写和页迁移等原始事件重新计算加权成本，并检查访问计数、页进入、降级数量、容量和分层状态是否守恒。表格中的 `Rank changes` 表示 CAPD 有多少轮没有直接采用 LRU 顺序，而是由模型改变了同轮候选页的选择。它只说明模型实际参与了决策，不表示这个合成负载上的性能提升。

第五步口播：

> 最后，完整流程会再运行一遍，并比较排除计时字段后的语义摘要。只有输入、状态演化、事件计数和选择结果完全一致，才会输出 `DEMO_CLOSED_LOOP_PASS`。

python -m json.tool "outputs/capd_demo/$RUN_ID/verification.json"

收尾句：

> 以上就是 CAPD 模块的实验仓库和功能闭环。它覆盖了从数据处理、模型训练冻结，到统一回放、指标重算、自动测试和证据归档的完整流程。

## 演示闭环的准确解释

闭环可以概括为：

```text
配置与模型身份校验
        -> 生成独立演示输入
        -> 多策略共享状态机运行
        -> 从原始事件重算指标
        -> 守恒关系检查
        -> 重复运行并比较语义摘要
        -> 保存 manifest / results / verification
```

`DEMO_CLOSED_LOOP_PASS` 只表示本次合成演示的输入、执行、指标、自检和复现链路通过。它不升级、不替代，也不复现正式实验的验证状态。

## 可删减与加时方案

如果总时长接近 5 分钟，优先删减各目录的具体文件名，只保留五类职责和闭环五步。不要删掉合成输入边界、共享状态机、成本重算和重复运行检查。

如果录制不足 3 分钟，可在仓库导览部分补充两点：一是配置文件与结果 Schema 如何防止实验口径漂移；二是 manifest、run state 和 verification 如何支持结果追溯。不要用演示表格临时展开性能比较。

## 录制注意事项

- 不把演示表格中的数值称为正式实验结果、加速比或性能提升比例。
- 不逐个介绍内部 Stage 编号；按五类功能模块讲解更容易理解。
- 不打开大体积 checkpoint、trace 或完整 JSON，只展示路径、摘要和验证状态。
- 保留开头与结尾的 `NON-FORMAL SYNTHETIC RUN` 和 `NOT formal experiment evidence` 提示。
- 重录时让脚本自动创建新的时间戳目录，不覆盖之前产物。
- 使用 GPU 时可改为 `--device cuda`，但应提前完整预演；演示口径仍然是同步回放，不是实际异步系统性能。
